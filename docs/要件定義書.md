# 転職コンパス（仮称） 要件定義書

> 名称は仮。「転職の軸を定め、選考機会を逃さず、意思決定に迷わない状態を作る」ためのWebアプリ。

## 1. プロジェクト概要

- **名称（仮）**: 転職コンパス
- **種別**: Webアプリ（個人開発、実用最優先＋実務レベルの開発スキル習得も兼ねる）
- **開始日**: 2026-07-26
- **姉妹プロジェクト**: 散歩記事化アプリ（`/home/mount/walk-article-app/`）。運用パターン（要件定義書をSSOTにする、決定ログを残す）を踏襲している。
- **タスクトラッカー**: https://claude.ai/code/artifact/67a7602c-56fb-4416-91ba-14b3772fe107 （「転職コンパス」タブ、10週・60タスク）
- **ワイヤーフレーム（Step1〜4）**: https://claude.ai/code/artifact/36930841-f491-4e2a-8d28-71e34383108e

## 2. 目的・ゴール

- 転職活動における「軸」（価値観・譲れない条件・優先順位）を言語化し、求人選びや意思決定で迷わない状態を作る
- 選考プロセス・スケジュールを一元管理し、対応漏れによる機会損失をなくす
- 上記を土台に、求人の比較・スコアリングや面接/ES対策までを軸に沿って一貫してサポートする
- 一次目的は自分自身の転職活動を成功させること。将来的に同じ課題を持つ他ユーザーへの公開も視野に入れた設計にする（無理な先取り実装はしない）

## 3. ターゲットユーザー・利用シーン

- **一次ユーザー**: 自分自身。現在すでに転職活動中（応募・選考が並行して動いている状態）
- **将来的な想定ユーザー**（Phase外・設計配慮のみ）: 同様に「軸が定まらない」「選考管理が煩雑」で困っている転職検討者

## 4. スコープ

### Phase 1（MVP）
- 軸の言語化フレームワーク（価値観・スキル・譲れない条件・優先順位を整理し、言語化された「軸」を出力する）
- 選考プロセス管理（応募〜書類選考〜面接〜内定までのステータス管理）
- スケジュール管理（面接日程・締切等のトラッキング）

### Phase 2
- 求人の比較・スコアリング（Phase 1で定めた軸に沿って求人を点数化・比較）

### Phase 3
- 面接・ES対策支援（軸・職務経歴を踏まえ、AI＝Claude APIを使った壁打ち・添削支援）

### スコープ外（当面採用しない）
- 他ユーザーとのSNS的共有・コミュニティ機能
- 求人検索エンジン自体の構築（求人情報は外部サイトからの手動転記/貼り付けを想定）
- モバイルネイティブアプリ化（まずWebのみ。将来必要になれば別途検討）

## 5. ユーザーフロー

### 5-1. 軸言語化フロー（Step1〜4）

```
Step1 自己理解
  ├─ Will-Can-Must自由記述（＋アプローチスタイル: 得意な仕事の進め方の粒度を追加質問）
  ├─ キャリアアンカー診断（8種×2問=16問、選択式）
  │    └─ 上位アンカーが3つ以上同点の場合は「回答の一貫性」を疑い再診断を促す
  └─ 動機タイプ選択（防衛型／成長型／脱出型／挑戦型 等から選択＋自由記述補足）
      ↓
Step2 Must条件登録
  └─ 絶対条件をカテゴリ問わず自由に追加（年収下限・勤務地・労働時間上限・NG業界/職種・企業規模 等）
      ↓
Step3 Want条件・移行戦略
  ├─ 標準7カテゴリへ合計100点の重み配分（仕事内容・やりがい／年収・待遇／働き方／企業文化・人間関係／成長・キャリアパス／安定性・将来性／企業規模・ネームバリュー）
  │    ※カテゴリはユーザーが追加可能。追加時は再配分を促す
  └─ キャリア移行戦略：入口の武器／将来像（North Star、時間軸指定可）／許容できる移行パス（複数選択：社内異動・副業・資格取得・転籍 等）
      ↓
Step4 軸カード生成
  └─ Must条件リスト＋Want重みテーブル＋キャリアアンカー上位＋動機タイプ＋移行戦略＋短期Must/中長期North Starのサマリーを1枚のカードとして出力
```

### 5-2. 選考プロセス管理フロー（Phase1）

軸カード確定後、応募先ごとに選考ステータス（応募〜書類選考〜面接〜内定/不採用）とスケジュール（面接日程・締切）を登録・更新する。Step4で出したMust条件と照らして、条件を満たさない応募先には警告を出す（Phase2の求人比較機能への布石）。

## 7. システム構成（アーキテクチャ）

- フロントエンド／API: Next.js（React + TypeScript）で1リポジトリに統合、Vercelにホスティング
- DB／認証: Supabase（Postgres + Auth）
- **方針**: Supabase Realtime（常時接続・ポーリング系機能）は使用しない。1人利用の求人管理にリアルタイム同期は不要であり、以前の個人開発（散歩記事化アプリ）でポーリング構造がUpstash Redis無料枠を数日で使い切った実インシデントがあるため、同種の構造的リスクを避ける
- Phase 3: Claude APIをサーバーサイド（Next.js API Route）経由で呼び出す。クライアントから直接APIキーを叩かせない

## 9. 調査結果と対応方針

### 9-1. コスト検証（2026-07-26実施）→【結論】Phase 1・2は実質¥0で運用可能

- **Vercel（Hobby）**: 100GB転送/月・Function実行100万回/月など、個人利用の負荷では十分な無料枠。上限超過時は従量課金にはならず、次の請求サイクル（約30日）までその機能が一時停止するだけ（サプライズ請求が発生しない設計）。唯一の制約はHobbyプランが非商用・個人利用限定である点で、将来「公開」が収益化を伴う場合はPro（$20/月〜）へのアップグレードが必要になる（ポートフォリオ的公開の間は問題なし）
- **Supabase（Free）**: DB 500MB・ファイル1GB・転送5GB/月など、個人の求人・選考データ量では余裕を持って収まる規模。7日間APIアクセスがないと自動一時停止する（データは保持、手動再開が必要）が、転職活動中は日常的に使うため実害は低い想定
- **Phase 3（Claude API）のみ従量課金**: Anthropic Consoleはワークスペース単位で入金制のスペンドリミットを設定可能（Tier 1は$5からの入金で開始）。後払い自動課金ではなくプリペイド型に近く、「前払いで被害上限を区切る」という個人開発の方針に合致する。Phase 3着手時に少額（$5〜10目安）から開始し、利用頻度を見て調整する方針とする

出典: Vercel/Supabase/Anthropic各社の公式ドキュメント・解説記事（2026年7月時点の情報）

## 10. 非機能要件

### コスト
- Phase 1・2は無料枠内での運用を前提とする。新しい外部サービス・従量課金の仕組みを追加する際は、無料枠で足りるか・異常系での請求青天井リスクがないかを事前検討してから導入する
- Phase 3のAI機能はAnthropic Consoleの入金制スペンドリミットで上限を明確に区切る。カード自動課金ではなくプリペイド運用を優先する

### セキュリティ
- 転職活動の内容（応募先企業名、選考状況、年収条件等）は機微度の高い個人情報。将来他ユーザーに公開する場合は、ユーザーごとのデータ分離（Row Level Security等）を前提に設計する

## 13. API仕様（エンドポイント一覧）

全エンドポイントはNext.js API Routes。認証はSupabaseのJWTをミドルウェアで検証し`user_id`を取得、加えてSupabase RLSでも二重にユーザー分離する。MVPは1人あたりのレコード数が少ない前提のためページネーションは実装せず全件返却とし、必要になった時点で追加する。

### 認証
サインアップ・ログイン・セッション管理はカスタムAPIを作らず、Supabase Auth SDKをクライアントから直接利用する。サーバー側は各APIのミドルウェアでSupabaseのJWTを検証するのみ。

### 軸プロファイル（Step1〜4）

| Method | Path | 概要 |
|---|---|---|
| GET | /api/axis/profile | Will-Can-Must・アプローチスタイル・動機タイプ・移行戦略を取得 |
| PUT | /api/axis/profile | 上記を更新（Step1・Step3後半の保存） |
| POST | /api/axis/anchor-answers | キャリアアンカー診断16問の回答を送信。サーバー側で8アンカー分のスコアを計算し`axis_anchor_scores`へ保存（生の回答は永続化しない） |
| GET | /api/axis/anchor-scores | 診断結果（8アンカーのスコア）を取得。上位が3つ以上同点の場合`needsRediagnosis: true`を返す |
| GET | /api/axis/must-conditions | Must条件一覧取得 |
| POST | /api/axis/must-conditions | Must条件を追加 |
| PATCH | /api/axis/must-conditions/:id | 編集 |
| DELETE | /api/axis/must-conditions/:id | 削除 |
| GET | /api/axis/want-categories | Wantカテゴリ・重み一覧取得（標準7＋カスタム） |
| PUT | /api/axis/want-categories | 重み配分を一括更新。合計が100でない場合`400 VALIDATION_ERROR` |
| POST | /api/axis/want-categories | カスタムカテゴリを追加（`is_custom: true`） |
| DELETE | /api/axis/want-categories/:id | カスタムカテゴリ削除。標準7カテゴリ（`is_custom: false`）の削除は`403 FORBIDDEN` |
| GET | /api/axis/card | Step4「軸カード」：上記すべてを統合したサマリーを返す（読み取り専用の集約エンドポイント） |

### 選考プロセス管理

| Method | Path | 概要 |
|---|---|---|
| GET | /api/selections | 一覧取得。`?status=`でフィルタ可 |
| POST | /api/selections | 応募先を新規登録 |
| GET | /api/selections/:id | 詳細取得（`must_condition_check`を含む） |
| PATCH | /api/selections/:id | ステータス・情報の更新 |
| DELETE | /api/selections/:id | 削除 |
| POST | /api/selections/:id/check-must-conditions | `axis_must_conditions`と照合し`must_condition_check`を再計算・保存 |

### スケジュール管理

| Method | Path | 概要 |
|---|---|---|
| GET | /api/schedules | 一覧取得。`?from=&to=`で期間フィルタ、`?selectionId=`で選考先フィルタ |
| POST | /api/schedules | 新規登録 |
| GET | /api/schedules/:id | 詳細取得 |
| PATCH | /api/schedules/:id | 更新 |
| DELETE | /api/schedules/:id | 削除 |

### エラーレスポンス共通形式

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Want重み配分の合計が100になっていません",
    "details": {}
  }
}
```

| HTTPステータス | code例 | 用途 |
|---|---|---|
| 400 | VALIDATION_ERROR | 入力値不正（重み合計不一致 等） |
| 401 | UNAUTHORIZED | 未ログイン・トークン不正 |
| 403 | FORBIDDEN | 標準カテゴリの削除等、許可されない操作 |
| 404 | NOT_FOUND | 対象リソースが存在しない、または他ユーザーのもの |
| 500 | INTERNAL_ERROR | サーバー側エラー |
